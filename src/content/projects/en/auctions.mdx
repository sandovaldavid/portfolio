<CaseStudySection eyebrow="PUBLIC EVIDENCE" title="The source repository is the current evidence surface">
  The repository contains the Django models, views, forms, templates, administrative analytics and deployment configuration for the auction workflow. An older README still shows a placeholder Heroku demo URL, but the portfolio does not present that placeholder as a live deployment.
</CaseStudySection>

<CaseStudySection eyebrow="PROBLEM" title="An auction is a lifecycle, not only a CRUD screen">
  Listings need an owner, a starting price, active/inactive state and a winner. Participants need to place bids, follow listings and comment without being able to close someone else's auction. The application models those relationships explicitly and keeps the core workflow server-rendered rather than introducing a separate SPA and API for an educational monolith.
</CaseStudySection>

<CaseStudySection eyebrow="WORKFLOW" title="Core auction mechanics live near the model and views">
  <CaseStudyGrid columns={3}>
    <CaseStudyCard label="BIDDING" title="A NEW BID MUST EXCEED THE CURRENT BID" tone="primary">
      `Listing.place_bid` rejects a value that is less than or equal to the current bid, updates `current_bid` and creates the corresponding `Bid` record.
    </CaseStudyCard>

    <CaseStudyCard label="OWNERSHIP" title="ONLY THE LISTING OWNER CAN CLOSE" tone="primary">
      The close view checks that the authenticated caller owns the listing. It then selects the highest recorded bid as winner, marks the listing inactive and persists the result.
    </CaseStudyCard>

    <CaseStudyCard label="DISCOVERY" title="CATEGORIES AND WATCHLISTS STAY SERVER-RENDERED" tone="primary">
      Active listings are paginated, category pages filter server-side and each authenticated user can toggle watchlist entries without a separate frontend state store.
    </CaseStudyCard>
  </CaseStudyGrid>
</CaseStudySection>

<CaseStudySection eyebrow="PERSISTENCE" title="Local SQLite and environment-driven PostgreSQL share one Django model" surface="highlight">
  The settings module uses SQLite by default for local development and switches to a `DATABASE_URL` configuration through `dj-database-url` when one is provided. Production-oriented configuration also includes Gunicorn, WhiteNoise and secure cookie/header settings in the repository dependencies and Django settings.
</CaseStudySection>

    <EvidenceBlock label="VERIFIED ADMIN TOOLING" title="PANDAS · PLOTLY · SCIKIT-LEARN ANALYTICS MODULE" tone="verified">
      The maintained repository includes analytics dependencies and an `AuctionAnalytics` module used by admin routes. This is presented as implementation evidence for administrative analysis tooling, not as proof that predictive models have production accuracy or business impact.
    </EvidenceBlock>

    <EvidenceBlock label="BOUNDARY" title="NO LIVE DEMO OR CONCURRENCY GUARANTEE" tone="boundary">
      The repository's old hosted-demo text is a placeholder rather than a current verifiable deployment. The bid rule performs a read/check/update sequence without explicit row locking or a transaction boundary in `place_bid`, so this case study does not call the current implementation concurrency-safe.
    </EvidenceBlock>

    <EvidenceBlock label="BOUNDARY" title="NO CURRENT DRF OR WEBSOCKET CLAIM" tone="boundary">
      Release history records experiments with APIs and realtime notifications, but the current `develop` requirements, installed apps, ASGI wiring and URL configuration do not expose DRF or Django Channels as the active application surface. Executable state wins over historical changelog wording.
    </EvidenceBlock>
  </CaseStudyGrid>
</CaseStudySection>

<CaseStudySection eyebrow="TRADE-OFFS" title="Server-rendered Django keeps the core workflow understandable" surface="highlight">
  Django templates, forms, sessions and ORM provide one deployable application and a short path from request to persisted state. The admin analytics layer adds useful operational inspection without requiring a second frontend, while richer real-time bidding and stronger concurrent-bid guarantees would still require additional design.
</CaseStudySection>

<CaseStudySection eyebrow="LEARNINGS" title="What this project made concrete">
  <CaseStudyGrid columns={3}>
    <CaseStudyCard label="LEARNING 01" title="MODEL THE LIFECYCLE, NOT ONLY THE TABLES" tone="success">
      Listing ownership, active state and winner selection make the closing transition explicit instead of treating an auction as generic CRUD data.
    </CaseStudyCard>

    <CaseStudyCard label="LEARNING 02" title="VALIDATION IS NOT THE SAME AS CONCURRENCY CONTROL" tone="success">
      Checking that a bid exceeds the current value is necessary, but simultaneous writes need their own transaction and locking strategy if the application must guarantee ordering under contention.
    </CaseStudyCard>

    <CaseStudyCard label="LEARNING 03" title="HISTORY IS NOT THE SAME AS CURRENT WIRING" tone="success">
      Changelogs can preserve experiments that the current dependency graph no longer exposes. A case study should read executable settings, routes and manifests before turning historical features into present-tense claims.
    </CaseStudyCard>
  </CaseStudyGrid>
</CaseStudySection>
