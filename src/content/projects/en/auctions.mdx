<CaseStudySection eyebrow="CURRENT PRODUCT" title="A maintained server-rendered auction workflow">
	The application combines Django models, forms, views and templates for authenticated listings, bids, watchlists, comments, categories and owner-controlled auction closing. Administrative analytics extend the original workflow, while the repository does not currently expose a live hosted demo.
</CaseStudySection>

<CaseStudySection eyebrow="PROBLEM" title="An auction is a lifecycle, not only a CRUD screen">
	Listings need an owner, a starting price, active/inactive state and a winner. Participants need to place bids, follow listings and comment without being able to close someone else's auction. The application models those relationships explicitly and keeps the core workflow server-rendered rather than introducing a separate SPA and API for an educational monolith.
</CaseStudySection>

<CaseStudySection eyebrow="WORKFLOW" title="Core auction mechanics live near the model and views">
  <CaseStudyGrid columns={3}>
    <CaseStudyCard label="BIDDING" title="A NEW BID MUST EXCEED THE CURRENT BID" tone="primary">
      `Listing.place_bid` rejects a value that is less than or equal to the current bid, updates `current_bid` and creates the corresponding `Bid` record.
    </CaseStudyCard>
    <CaseStudyCard label="OWNERSHIP" title="ONLY THE LISTING OWNER CAN CLOSE" tone="primary">
      The close view checks that the authenticated caller owns the listing. It then selects the highest recorded bid as winner, marks the listing inactive and persists the result.
    </CaseStudyCard>
    <CaseStudyCard label="DISCOVERY" title="CATEGORIES AND WATCHLISTS STAY SERVER-RENDERED" tone="primary">
      Active listings are paginated, category pages filter server-side and each authenticated user can toggle watchlist entries without a separate frontend state store.
    </CaseStudyCard>
  </CaseStudyGrid>
</CaseStudySection>

<CaseStudySection eyebrow="PERSISTENCE" title="Local SQLite and environment-driven PostgreSQL share one Django model" surface="highlight">
	The settings module uses SQLite by default for local development and switches to a `DATABASE_URL` configuration through `dj-database-url` when one is provided. Deployment-oriented configuration also includes Gunicorn, WhiteNoise and secure cookie/header settings.
</CaseStudySection>

<CaseStudySection eyebrow="CURRENT BOUNDARIES" title="What the maintained implementation guarantees — and what still needs design">
  <CaseStudyGrid columns={2}>
    <EvidenceBlock label="APPLICATION STACK" title="DJANGO 5.1–5.2 · AUTH · FORMS · ORM" tone="verified">
      `requirements.txt` constrains Django to the 5.1–5.2 range and includes PostgreSQL, Gunicorn and WhiteNoise support. The code contains the `User`, `Listing`, `Bid`, `Comment` and `Watchlist` models together with the listing, bidding, category, comment and closing workflows.
    </EvidenceBlock>
    <EvidenceBlock label="ADMIN TOOLING" title="PANDAS · PLOTLY · SCIKIT-LEARN ANALYTICS" tone="verified">
      The maintained codebase includes analytics dependencies and an `AuctionAnalytics` module used by administrative routes. Its prediction path explicitly handles insufficient data instead of treating a small sample as a reliable model.
    </EvidenceBlock>
    <EvidenceBlock label="CONCURRENCY" title="BID VALIDATION IS NOT A CONCURRENCY GUARANTEE" tone="boundary">
      The bid rule uses a read/check/update sequence without explicit row locking or a transaction boundary in `place_bid`. Strong guarantees for simultaneous bids would require an additional transactional and locking strategy.
    </EvidenceBlock>
    <EvidenceBlock label="ACTIVE SURFACE" title="DRF AND WEBSOCKETS ARE NOT CURRENTLY WIRED" tone="boundary">
      Historical release notes include API and realtime experiments, but the maintained `develop` dependency graph, installed apps, ASGI wiring and URLs do not expose DRF or Django Channels as part of the active application surface.
    </EvidenceBlock>
  </CaseStudyGrid>
</CaseStudySection>

<CaseStudySection eyebrow="TRADE-OFFS" title="Server-rendered Django keeps the core workflow understandable" surface="highlight">
	Django templates, forms, sessions and ORM provide one deployable application and a short path from request to persisted state. The admin analytics layer adds operational inspection without requiring a second frontend, while richer real-time bidding and stronger concurrent-bid guarantees would require additional design.
</CaseStudySection>

<CaseStudySection eyebrow="LEARNINGS" title="What this project made concrete">
  <CaseStudyGrid columns={3}>
    <CaseStudyCard label="LEARNING 01" title="MODEL THE LIFECYCLE, NOT ONLY THE TABLES" tone="success">
      Listing ownership, active state and winner selection make the closing transition explicit instead of treating an auction as generic CRUD data.
    </CaseStudyCard>
    <CaseStudyCard label="LEARNING 02" title="VALIDATION IS NOT THE SAME AS CONCURRENCY CONTROL" tone="success">
      Checking that a bid exceeds the current value is necessary, but simultaneous writes need their own transaction and locking strategy if the application must guarantee ordering under contention.
    </CaseStudyCard>
    <CaseStudyCard label="LEARNING 03" title="MAINTAINED CONFIGURATION MUST MATCH DOCUMENTED CAPABILITIES" tone="success">
      Experiments can outlive the dependencies that enabled them. Keeping release notes, active wiring and documentation aligned prevents retired capabilities from remaining part of the perceived system boundary.
    </CaseStudyCard>
  </CaseStudyGrid>
</CaseStudySection>
