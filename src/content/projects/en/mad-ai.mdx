<CaseStudySection eyebrow="SYSTEM BOUNDARY" title="A public Angular client and a separately maintained private API">
	MAD AI is split across two repositories. The Angular client contains the SSR entry point, routed administrative UI, explicit client-side layers and HTTP adapters. A separate Django REST service owns backend application and persistence concerns. The repositories can evolve independently while meeting at the REST contract.
</CaseStudySection>

<CaseStudySection eyebrow="PROBLEM" title="Administrative workflows accumulate cross-cutting concerns quickly">
	Authentication, guarded navigation, user administration, roles, notifications and reporting all need shared application behavior without turning routed components into transport clients. The project separates those concerns at both ends: an Angular client with explicit layers and a Django REST service with its own application/domain/infrastructure boundaries.
</CaseStudySection>

<CaseStudySection eyebrow="FRONTEND" title="Layer names correspond to real Angular boundaries">
  <CaseStudyGrid columns={2}>
    <CaseStudyCard label="DOMAIN" title="CONTRACTS BEFORE TRANSPORT" tone="primary">
      Domain entities and repository abstractions define what authentication, users, roles and notifications need without embedding endpoint details into routed components.
    </CaseStudyCard>
    <CaseStudyCard label="APPLICATION" title="USE CASES COORDINATE INTENT" tone="primary">
      Application code sits between presentation and infrastructure so UI flows express actions through use cases instead of binding every component directly to HTTP mechanics.
    </CaseStudyCard>
    <CaseStudyCard label="INFRASTRUCTURE" title="HTTP REPOSITORIES ADAPT THE API" tone="primary">
      Concrete implementations for authentication, notifications, roles and users own DTO/API interaction behind repository contracts. Environment configuration points those adapters to `/api/v1`.
    </CaseStudyCard>
    <CaseStudyCard label="PRESENTATION" title="ROUTES DEFINE PUBLIC AND SECURED AREAS" tone="primary">
      Authentication routes use their own layout, while dashboard and user-management surfaces sit behind `AuthGuard` inside the secured shell. Angular SSR and Express provide the server-rendered entry path.
    </CaseStudyCard>
  </CaseStudyGrid>
</CaseStudySection>

<CaseStudySection eyebrow="BACKEND" title="The API uses a pragmatic modular Django architecture" surface="highlight">
  The backend dependency manifest pins **Django 5.2.3** and **Django REST Framework 3.16.0**, with JWT/cryptography support, PostgreSQL through `psycopg2`, filtering, OpenAPI tooling and Celery. Its architecture documentation describes a hybrid modular approach combining a service layer, domain-centric Django models and ports/adapters rather than forcing a framework-neutral domain that duplicates the ORM.

The API is maintained in a private repository, so its implementation remains a separate delivery boundary from the open-source client. The client-facing story therefore concentrates on the REST contract and the responsibilities assigned to each side of that boundary.
</CaseStudySection>

<CaseStudySection eyebrow="REPORTING" title="The client owns visualization and export concerns">
	The Angular manifest includes ECharts, jsPDF and PapaParse. Keeping charting and export libraries in the client lets reporting surfaces transform API responses into interactive visualizations and downloadable representations without pushing presentation concerns back into the REST service.
</CaseStudySection>
