<CaseStudySection eyebrow="EVIDENCE BOUNDARY" title="The client is public; the companion API is private" width="reading">
  <ProjectResources projectId="mad-ai" resources={['source']} />

  The public `MAD-AI` repository exposes the Angular application, SSR entry point, layered client architecture and HTTP adapters. A separate `MAD-AI-API` repository contains the Django REST service, but that repository is private. This case study uses the private backend as owner-verifiable context while keeping the public-source badge linked only to the frontend that a recruiter can inspect independently.
</CaseStudySection>

<CaseStudySection eyebrow="PROBLEM" title="Administrative workflows accumulate cross-cutting concerns quickly">
  Authentication, guarded navigation, user administration, roles, notifications and reporting all need shared application behavior without turning routed components into transport clients. The project separates those concerns at both ends: an Angular client with explicit layers and a Django REST service with its own application/domain/infrastructure boundaries.
</CaseStudySection>

<CaseStudySection eyebrow="FRONTEND" title="Layer names correspond to real Angular boundaries">
  <CaseStudyGrid columns={2}>
    <CaseStudyCard label="DOMAIN" title="CONTRACTS BEFORE TRANSPORT" tone="primary">
      Domain entities and repository abstractions define what authentication, users, roles and notifications need without embedding endpoint details into routed components.
    </CaseStudyCard>

    <CaseStudyCard label="APPLICATION" title="USE CASES COORDINATE INTENT" tone="primary">
      Application code sits between presentation and infrastructure so UI flows express actions through use cases instead of binding every component directly to HTTP mechanics.
    </CaseStudyCard>

    <CaseStudyCard label="INFRASTRUCTURE" title="HTTP REPOSITORIES ADAPT THE API" tone="primary">
      Concrete implementations for authentication, notifications, roles and users own DTO/API interaction behind repository contracts. Environment configuration points those adapters to `/api/v1`.
    </CaseStudyCard>

    <CaseStudyCard label="PRESENTATION" title="ROUTES DEFINE PUBLIC AND SECURED AREAS" tone="primary">
      Authentication routes use their own layout, while dashboard and user-management surfaces sit behind `AuthGuard` inside the secured shell. Angular SSR and Express provide the server-rendered entry path.
    </CaseStudyCard>
  </CaseStudyGrid>
</CaseStudySection>

<CaseStudySection eyebrow="BACKEND" title="The private API uses a pragmatic modular Django architecture" surface="highlight">
  The backend dependency manifest pins **Django 5.2.3** and **Django REST Framework 3.16.0**, with JWT/cryptography support, PostgreSQL through `psycopg2`, filtering, OpenAPI tooling and Celery. Its architecture document describes a hybrid modular approach that combines a service layer, domain-centric Django models and ports/adapters rather than forcing a framework-neutral domain that duplicates the ORM.

  Because the repository is private, these facts are not presented as independently inspectable public evidence. They explain the architecture I built and maintain; the public client remains the evidence surface available to external reviewers.
</CaseStudySection>

<CaseStudySection eyebrow="REPORTING" title="The client owns visualization and export concerns">
  The Angular manifest includes ECharts, jsPDF and PapaParse. Keeping charting/export libraries in the client lets reporting surfaces transform API responses into interactive visualizations and downloadable representations without pushing presentation concerns back into the REST service.
</CaseStudySection>
