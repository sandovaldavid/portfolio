<CaseStudySection eyebrow="PROBLEM" title="Shared household money still contains private information">
  A household finance product has to represent obligations that are genuinely shared while preventing one member's private financial records from becoming household-wide data by default. Cards, debts, income, budgets and recommendations also need one authoritative calculation path instead of slightly different formulas in every client.

Yukidoke therefore treats **authentication**, **household membership** and **per-record financial visibility** as separate boundaries rather than one generic “logged-in user” check.

</CaseStudySection>

<CaseStudySection eyebrow="ARCHITECTURE" title="A modular monolith keeps V1 transactions understandable">
  <CaseStudyGrid columns={3}>
    <CaseStudyCard label="BOUNDARY 01" title="KEYCLOAK OWNS IDENTITY" tone="primary">
      The browser is a public OIDC client using Authorization Code + PKCE. Global identity is deliberately separated from household membership and financial permissions.
    </CaseStudyCard>

    <CaseStudyCard label="BOUNDARY 02" title="THE API OWNS FINANCIAL RULES" tone="primary">
      The Angular client expresses intent and renders state. Household permissions, accounting behavior, financial-health calculations and durable read models belong to the API rather than being duplicated in the browser.
    </CaseStudyCard>

    <CaseStudyCard label="BOUNDARY 03" title="POSTGRESQL OWNS DURABLE STATE" tone="primary">
      Modules persist through PostgreSQL with EF Core migrations and optimistic concurrency. The database migrator is the process responsible for applying migrations instead of every application process mutating schema on startup.
    </CaseStudyCard>

  </CaseStudyGrid>
</CaseStudySection>

<CaseStudySection eyebrow="DATA FLOW" title="REST recovers truth; realtime is incremental">
  The web repository documents typed REST clients, pagination normalization and ProblemDetails handling. Notification state is designed to recover from durable REST state and use SignalR for incremental updates, so losing a realtime connection does not redefine the source of truth.

This distinction matters in finance: a websocket event can improve responsiveness, but it should not be the only record that a balance, notification or household action exists.

</CaseStudySection>

<CaseStudySection eyebrow="PRIVACY" title="Resource existence is part of the authorization model">
  The API documentation explicitly allows household-scoped endpoints to conceal a resource from non-members rather than revealing that it exists. That is a stronger privacy boundary than simply returning “forbidden” after exposing an identifier.

Hardening remains active around privacy enforcement, export and directory surfaces, balances and settlements, final authentication acceptance and production-readiness gates on a clean stack. Those areas define the current beta boundary rather than being presented as finished production behavior.

</CaseStudySection>

<CaseStudySection eyebrow="LEARNINGS" title="Engineering lessons from the household boundary">
  <CaseStudyGrid columns={3}>
    <CaseStudyCard label="LEARNING 01" title="AUTHENTICATION IS NOT AUTHORIZATION" tone="success">
      Identity, household membership and visibility of a specific financial record need independent rules and independent tests.
    </CaseStudyCard>

    <CaseStudyCard label="LEARNING 02" title="REALTIME SHOULD NOT OWN DURABILITY" tone="success">
      SignalR is useful for incremental updates; recoverable REST state remains the safer authority when a realtime connection drops or reconnects.
    </CaseStudyCard>

    <CaseStudyCard label="LEARNING 03" title="A MODULAR MONOLITH CAN BE A DELIBERATE CHOICE" tone="success">
      Domain boundaries, migration ownership and transaction consistency can be explicit without paying the operational cost of distributed services before V1 needs them.
    </CaseStudyCard>

  </CaseStudyGrid>
</CaseStudySection>
