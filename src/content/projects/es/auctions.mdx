  <ProjectResources projectId="auctions" resources={['source']} />

  El repositorio contiene modelos, vistas, formularios, templates y configuración de despliegue Django para el flujo de subastas. Un README antiguo todavía muestra una URL placeholder de Heroku, pero el portfolio no presenta ese placeholder como un despliegue en vivo.
</CaseStudySection>

<CaseStudySection eyebrow="PROBLEMA" title="Una subasta es un ciclo de vida, no sólo una pantalla CRUD">
  Los listings necesitan propietario, precio inicial, estado activo/inactivo y ganador. Los participantes necesitan pujar, seguir listings y comentar sin poder cerrar una subasta ajena. La aplicación modela esas relaciones explícitamente y mantiene el workflow principal server-rendered en lugar de introducir una SPA y API separadas para un monolito educativo.
</CaseStudySection>

<CaseStudySection eyebrow="PERSISTENCIA" title="SQLite local y PostgreSQL por entorno comparten el mismo modelo Django" surface="highlight">
  El módulo de settings usa SQLite por defecto para desarrollo local y cambia a una configuración `DATABASE_URL` mediante `dj-database-url` cuando existe. Las dependencias y settings también incluyen Gunicorn, WhiteNoise y configuración de cookies/headers de seguridad para escenarios de producción.
</CaseStudySection>

<CaseStudySection eyebrow="EVIDENCIA" title="Qué es verificable hoy">
  <CaseStudyGrid columns={2}>
    <EvidenceBlock label="VERIFICADO EN CÓDIGO" title="DJANGO 5.1–5.2 · AUTH · FORMS · ORM" tone="verified">
      `requirements.txt` restringe Django al rango 5.1–5.2 e incluye soporte para PostgreSQL, Gunicorn y WhiteNoise. El código público expone directamente los modelos `User`, `Listing`, `Bid`, `Comment` y `Watchlist`, además de vistas para listings, pujas, categorías, comentarios y cierre de subastas.

    <EvidenceBlock label="LÍMITE" title="SIN DEMO EN VIVO NI GARANTÍA DE CONCURRENCIA" tone="boundary">
      El texto antiguo de demo alojada del repositorio es un placeholder y no un despliegue verificable actual. La regla de puja realiza una secuencia lectura/verificación/actualización sin row locking explícito ni un límite transaccional en `place_bid`, por lo que este caso de estudio no llama concurrency-safe a la implementación actual.
    </EvidenceBlock>
  </CaseStudyGrid>
</CaseStudySection>

<CaseStudySection eyebrow="TRADE-OFFS" title="Django server-rendered mantiene comprensible el alcance educativo" surface="highlight">
  Templates, forms, sesiones y ORM de Django proporcionan una sola aplicación desplegable y un recorrido corto desde request hasta estado persistido. El trade-off es que pujas en tiempo real y garantías más fuertes ante escrituras concurrentes necesitarían diseño adicional en vez de aparecer automáticamente en el monolito actual.
</CaseStudySection>
