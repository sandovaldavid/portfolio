<CaseStudySection eyebrow="EVIDENCIA PÚBLICA" title="El repositorio de código es la superficie verificable actual">
  El repositorio contiene modelos, vistas, formularios, templates, analítica administrativa y configuración de despliegue Django para el flujo de subastas. Un README antiguo todavía muestra una URL placeholder de Heroku, pero el portfolio no presenta ese placeholder como un despliegue en vivo.
</CaseStudySection>

<CaseStudySection eyebrow="PROBLEMA" title="Una subasta es un ciclo de vida, no sólo una pantalla CRUD">
  Los listings necesitan propietario, precio inicial, estado activo/inactivo y ganador. Los participantes necesitan pujar, seguir listings y comentar sin poder cerrar una subasta ajena. La aplicación modela esas relaciones explícitamente y mantiene el workflow principal server-rendered en lugar de introducir una SPA y API separadas para un monolito educativo.
</CaseStudySection>

<CaseStudySection eyebrow="PERSISTENCIA" title="SQLite local y PostgreSQL por entorno comparten el mismo modelo Django" surface="highlight">

<CaseStudySection eyebrow="EVIDENCIA" title="Qué es verificable hoy">
  <CaseStudyGrid columns={2}>
    <EvidenceBlock label="VERIFICADO EN CÓDIGO" title="DJANGO 5.1–5.2 · AUTH · FORMS · ORM" tone="verified">
      `requirements.txt` restringe Django al rango 5.1–5.2 e incluye soporte para PostgreSQL, Gunicorn y WhiteNoise. El código público expone directamente los modelos `User`, `Listing`, `Bid`, `Comment` y `Watchlist`, además de vistas para listings, pujas, categorías, comentarios y cierre de subastas.
    </EvidenceBlock>

    <EvidenceBlock label="TOOLING ADMIN VERIFICADO" title="MÓDULO DE ANALÍTICA CON PANDAS · PLOTLY · SCIKIT-LEARN" tone="verified">
      El repositorio mantenido incluye las dependencias analíticas y un módulo `AuctionAnalytics` consumido por las rutas administrativas. Esto se presenta como evidencia de tooling de análisis, no como prueba de precisión productiva de modelos predictivos ni impacto comercial.
    </EvidenceBlock>

    <EvidenceBlock label="LÍMITE" title="SIN DEMO EN VIVO NI GARANTÍA DE CONCURRENCIA" tone="boundary">
      El texto antiguo de demo alojada es un placeholder y no un despliegue verificable actual. La regla de puja realiza una secuencia lectura/verificación/actualización sin row locking explícito ni un límite transaccional en `place_bid`, por lo que este caso de estudio no llama concurrency-safe a la implementación actual.
    </EvidenceBlock>

    <EvidenceBlock label="LÍMITE" title="SIN CLAIM ACTUAL DE DRF O WEBSOCKETS" tone="boundary">
      El historial de releases conserva experimentos con APIs y notificaciones realtime, pero los requirements, apps instaladas, wiring ASGI y URLs del `develop` actual no exponen DRF ni Django Channels como superficie activa. El estado ejecutable prevalece sobre wording histórico del changelog.
    </EvidenceBlock>
  </CaseStudyGrid>
</CaseStudySection>

<CaseStudySection eyebrow="TRADE-OFFS" title="Django server-rendered mantiene comprensible el workflow principal" surface="highlight">
  Templates, forms, sesiones y ORM proporcionan una sola aplicación desplegable y un recorrido corto desde request hasta estado persistido. La capa de analítica administrativa añade inspección operativa útil sin requerir un segundo frontend, mientras pujas realtime y garantías fuertes ante escrituras concurrentes todavía necesitarían diseño adicional.
</CaseStudySection>
