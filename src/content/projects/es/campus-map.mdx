<CaseStudySection eyebrow="EVIDENCIA PÚBLICA" title="El repositorio actual define el límite del producto">
  El repositorio es un proyecto open-source independiente y no un producto oficial de la Universidad Nacional de Piura. Su superficie ejecutable actual es un directorio académico con búsqueda y administración de contenido; el mapa geoespacial interactivo descrito en la dirección de producto más antigua continúa como roadmap y no como capacidad entregada.
</CaseStudySection>

<CaseStudySection eyebrow="PROBLEMA" title="La información del campus es más útil cuando está estructurada y se puede buscar">
  Nombres de facultades, escuelas, referencias de pabellón y enlaces oficiales son más utilizables cuando viven en un directorio consultable en lugar de redescubrirse en páginas o documentos separados. La implementación se centra por ello en **descubrimiento de facultades y escuelas** sin afirmar un sistema de navegación interactivo que el código actual no entrega.
</CaseStudySection>

<CaseStudySection eyebrow="IMPLEMENTACIÓN" title="Qué soporta realmente el código">
  <CaseStudyGrid columns={3}>
    <CaseStudyCard label="DESCUBRIMIENTO" title="FACULTADES + ESCUELAS" tone="primary">
      La capa de servicios selecciona facultades, cuenta escuelas relacionadas y busca por nombre de facultad, descripción y nombre de escuela. Los registros de escuela exponen pabellón y sitio web oficial.
    </CaseStudyCard>

    <CaseStudyCard label="CONTENIDO" title="CRUD ADMINISTRATIVO" tone="primary">
      El árbol actual del App Router incluye un área administrativa y `facultyService` implementa create, update y delete sobre el mismo límite de persistencia utilizado por las lecturas públicas.
    </CaseStudyCard>

    <CaseStudyCard label="MEDIA + DATOS" title="CLOUDINARY + KNEX" tone="primary">
      La media se separa mediante Cloudinary. El acceso a datos se centraliza detrás de Knex y el repositorio incluye esquemas tanto para MySQL como PostgreSQL, en lugar de acoplar cada consulta a un único driver.
    </CaseStudyCard>
  </CaseStudyGrid>
</CaseStudySection>

<CaseStudySection eyebrow="DRIFT DE VERSIONES" title="Los manifests ejecutables tienen prioridad sobre tablas README desactualizadas" surface="highlight">
  <CaseStudyGrid columns={2}>
    <EvidenceBlock label="VERIFICADO EN PACKAGE MANIFEST" title="NEXT.JS 16 · REACT 19 · TAILWIND 4" tone="verified">
      El `package.json` actual usa Next.js **16.0.10**, React **19.2.3** y Tailwind CSS **4.1.17**. Secciones anteriores del README todavía mencionan Next.js 14 y MySQL 8, por lo que esas tablas antiguas no se utilizan como fuente de verdad técnica del portafolio.
    </EvidenceBlock>

    <EvidenceBlock label="LÍMITE" title="EL MAPA INTERACTIVO NO SE PRESENTA COMO ENTREGADO" tone="boundary">
      El roadmap del repositorio todavía describe el mapping interactivo y comportamiento geoespacial como trabajo futuro. Este caso de estudio **no** repite por ello los claims anteriores del portafolio sobre un motor de geolocalización, marcadores de mapa en vivo ni reducciones medidas del tiempo de orientación en campus.
    </EvidenceBlock>
  </CaseStudyGrid>
</CaseStudySection>

<CaseStudySection eyebrow="TRADE-OFFS" title="Primero el directorio, luego el mapa">
  Construir primero el modelo de datos, búsqueda y administración de contenido crea una capa de información verificable que un futuro mapa puede consumir. También evita acoplar el valor del proyecto a GPS o UX geoespacial antes de que los registros de facultades y escuelas sean confiables.

  Knex añade una pequeña capa de abstracción, pero entrega una superficie de consultas común para el MySQL configurado por defecto y la configuración compatible con PostgreSQL documentada por el repositorio.
</CaseStudySection>

<CaseStudySection eyebrow="APRENDIZAJES" title="Qué cambió al auditar el repositorio">

    </CaseStudyCard>

    <CaseStudyCard label="APRENDIZAJE 02" title="CONFIGURACIÓN EJECUTABLE ANTES QUE DOCUMENTACIÓN ANTIGUA" tone="success">
      Manifests, árboles de rutas y servicios son mejor evidencia de versiones y capacidades actuales cuando la prosa no ha seguido el ritmo de las actualizaciones de dependencias.
    </CaseStudyCard>

    <CaseStudyCard label="APRENDIZAJE 03" title="PORTABILIDAD NECESITA UN LÍMITE REAL" tone="success">
      Soportar más de una base de datos es más creíble cuando las consultas pasan por una sola capa adaptadora y existen ambos esquemas, no cuando la portabilidad sólo aparece en un README.
    </CaseStudyCard>
  </CaseStudyGrid>
