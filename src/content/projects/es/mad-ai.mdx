<CaseStudySection eyebrow="LÍMITE DEL SISTEMA" title="Un cliente Angular público y una API privada mantenida por separado">
	MAD AI está dividido en dos repositorios. El cliente Angular contiene el entry point SSR, la UI administrativa enrutada, capas explícitas del cliente y adaptadores HTTP. Un servicio Django REST separado controla aplicación y persistencia del backend. Ambos repositorios pueden evolucionar de forma independiente y se encuentran en el contrato REST.
</CaseStudySection>

<CaseStudySection eyebrow="PROBLEMA" title="Los flujos administrativos acumulan responsabilidades transversales rápidamente">
	Autenticación, navegación protegida, administración de usuarios, roles, notificaciones y reporting necesitan comportamiento compartido sin convertir los componentes en clientes de transporte. El proyecto separa estas responsabilidades en ambos extremos: un cliente Angular con capas explícitas y un servicio Django REST con sus propios límites de aplicación, dominio e infraestructura.
</CaseStudySection>

<CaseStudySection eyebrow="BACKEND" title="La API usa una arquitectura Django modular y pragmática" surface="highlight">
  El manifest del backend fija **Django 5.2.3** y **Django REST Framework 3.16.0**, con JWT/cryptography, PostgreSQL mediante `psycopg2`, filtering, tooling OpenAPI y Celery. Su documentación de arquitectura describe un enfoque híbrido modular que combina service layer, modelos Django centrados en dominio y ports/adapters en lugar de forzar un dominio agnóstico que duplique el ORM.

La API se mantiene en un repositorio privado, por lo que su implementación permanece como un límite de entrega separado del cliente open-source. La historia del sistema se concentra en el contrato REST y en las responsabilidades asignadas a cada lado de ese límite.
</CaseStudySection>

<CaseStudySection eyebrow="REPORTING" title="El cliente posee visualización y exportación">
	El manifest Angular incluye ECharts, jsPDF y PapaParse. Mantener charting y exportación en el cliente permite convertir respuestas de API en visualizaciones interactivas y representaciones descargables sin devolver preocupaciones de presentación al servicio REST.
</CaseStudySection>
