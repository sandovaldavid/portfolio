<CaseStudySection eyebrow="EVIDENCIA PÚBLICA" title="El repositorio frontend es el límite verificable" width="reading">
  <ProjectResources projectId="mad-ai" resources={['source']} />

  MAD AI se entiende mejor como un **cliente administrativo en Angular**, no como un despliegue full-stack verificado. El repositorio público contiene la aplicación Angular, la entrada de servidor SSR, la arquitectura frontend por capas, implementaciones de repositorios HTTP y notas de contratos de API. No contiene un backend Django ni un esquema PostgreSQL, por lo que este caso de estudio no presenta esas tecnologías como evidencia entregada del proyecto.
</CaseStudySection>

<CaseStudySection eyebrow="PROBLEMA" title="Los flujos administrativos acumulan responsabilidades transversales rápidamente">
  Autenticación, navegación protegida, administración de usuarios, roles y notificaciones necesitan compartir estado de aplicación sin convertir los componentes de presentación en clientes HTTP. La implementación separa estas responsabilidades en contratos de dominio, casos de uso de aplicación, adaptadores de infraestructura y rutas de presentación.
</CaseStudySection>

<CaseStudySection eyebrow="ARQUITECTURA" title="Los nombres de las capas corresponden a límites reales del repositorio">

    <CaseStudyCard label="APLICACIÓN" title="LOS CASOS DE USO COORDINAN LA INTENCIÓN" tone="primary">
      La capa de aplicación se ubica entre presentación e infraestructura para que los flujos UI expresen acciones mediante casos de uso en lugar de acoplar cada componente a la mecánica de endpoints.
    </CaseStudyCard>

    <CaseStudyCard label="INFRAESTRUCTURA" title="LOS REPOSITORIOS HTTP ADAPTAN LA API" tone="primary">

    </CaseStudyCard>

    <CaseStudyCard label="PRESENTACIÓN" title="LAS RUTAS SEPARAN ÁREAS PÚBLICAS Y PROTEGIDAS" tone="primary">
      `/auth` usa su propio layout, mientras dashboard y gestión de usuarios viven detrás de `AuthGuard` dentro del shell protegido.
    </CaseStudyCard>

<CaseStudySection eyebrow="AUTENTICACIÓN" title="El cliente documenta un contrato de API basado en tokens" surface="highlight">
  Las notas públicas de API describen login, logout, refresh token, registro, confirmación de correo y usuario actual. El environment frontend apunta a un servicio externo `/api/v1`, por lo que el portfolio trata esos archivos como **evidencia del contrato consumido por el cliente**, no como prueba de cómo el backend almacena usuarios o valida tokens internamente.
</CaseStudySection>

<CaseStudySection eyebrow="NOTIFICACIONES" title="Un workflow reutilizable de notificaciones atraviesa las mismas capas">
  El repositorio documenta notificaciones de éxito, error, advertencia e información con posiciones y cierre configurables. Para este caso de estudio, lo relevante es que esa feature sigue la misma separación dominio → aplicación → infraestructura → presentación en lugar de convertirse en un componente global aislado con conocimiento del transporte.
</CaseStudySection>

Por eso esta página no afirma Django, PostgreSQL, WebSockets, readiness de producción ni adopción.

<CaseStudySection eyebrow="APRENDIZAJES" title="Qué demuestra este repositorio" surface="highlight">

    </CaseStudyCard>

    <CaseStudyCard label="APRENDIZAJE 03" title="UN CONTRATO DE API DOCUMENTADO NO ES EVIDENCIA DEL BACKEND" tone="success">
