<CaseStudySection eyebrow="PROBLEMA" title="El dinero compartido del hogar todavía contiene información privada">
  Un producto de finanzas familiares debe representar obligaciones realmente compartidas sin convertir por defecto los registros financieros privados de cada miembro en datos visibles para todo el hogar. Tarjetas, deudas, ingresos, presupuestos y recomendaciones también necesitan una sola ruta autoritativa de cálculo, no fórmulas ligeramente distintas en cada cliente.

Yukidoke trata por ello **autenticación**, **membresía del hogar** y **visibilidad por registro financiero** como límites independientes, no como un único check de “usuario autenticado”.

</CaseStudySection>

<CaseStudySection eyebrow="ARQUITECTURA" title="Un monolito modular mantiene comprensibles las transacciones de V1">
  <CaseStudyGrid columns={3}>
    <CaseStudyCard label="LÍMITE 01" title="KEYCLOAK CONTROLA IDENTIDAD" tone="primary">
      El navegador es un cliente OIDC público que usa Authorization Code + PKCE. La identidad global se mantiene deliberadamente separada de la membresía del hogar y de los permisos financieros.
    </CaseStudyCard>

    <CaseStudyCard label="LÍMITE 02" title="LA API CONTROLA LAS REGLAS FINANCIERAS" tone="primary">
      El cliente Angular expresa intención y renderiza estado. Permisos por hogar, comportamiento contable, cálculos de salud financiera y read models durables pertenecen a la API en lugar de duplicarse en el navegador.
    </CaseStudyCard>

    <CaseStudyCard label="LÍMITE 03" title="POSTGRESQL CONTROLA EL ESTADO DURABLE" tone="primary">
      Los módulos persisten mediante PostgreSQL con migraciones EF Core y concurrencia optimista. El Database Migrator es el proceso responsable de aplicar migraciones en lugar de permitir que cada proceso de aplicación cambie el esquema al iniciar.
    </CaseStudyCard>

  </CaseStudyGrid>
</CaseStudySection>

<CaseStudySection eyebrow="FLUJO DE DATOS" title="REST recupera la verdad; realtime es incremental">
  El repositorio web documenta clientes REST tipados, normalización de paginación y manejo de ProblemDetails. El estado de notificaciones está diseñado para recuperarse desde estado durable por REST y usar SignalR para actualizaciones incrementales, de modo que perder una conexión realtime no redefina la fuente de verdad.

Esta diferencia importa en finanzas: un evento websocket puede mejorar la respuesta de la interfaz, pero no debería ser el único registro de que existe un balance, una notificación o una acción del hogar.

</CaseStudySection>

<CaseStudySection eyebrow="PRIVACIDAD" title="La existencia de un recurso forma parte del modelo de autorización">
  La documentación de la API permite explícitamente que endpoints con alcance por hogar oculten un recurso a quien no es miembro, en vez de revelar primero que existe y responder después con “forbidden”. Es un límite de privacidad más fuerte que una autorización genérica posterior a la resolución del identificador.

El trabajo de hardening restante también se presenta como evidencia del producto, no como polish oculto: enforcement de privacidad, superficies de exportación/directorio, balances y settlements, aceptación final de autenticación y gates de preparación productiva sobre un stack limpio continúan activos.

</CaseStudySection>

<CaseStudySection eyebrow="APRENDIZAJES" title="Lecciones de ingeniería del límite por hogar">
  <CaseStudyGrid columns={3}>
    <CaseStudyCard label="APRENDIZAJE 01" title="AUTENTICACIÓN NO ES AUTORIZACIÓN" tone="success">
      Identidad, membresía del hogar y visibilidad de un registro financiero específico necesitan reglas y pruebas independientes.
    </CaseStudyCard>

    <CaseStudyCard label="APRENDIZAJE 02" title="REALTIME NO DEBERÍA CONTROLAR LA DURABILIDAD" tone="success">
      SignalR es útil para actualizaciones incrementales; el estado recuperable por REST es una autoridad más segura cuando una conexión realtime se pierde o reconecta.
    </CaseStudyCard>

    <CaseStudyCard label="APRENDIZAJE 03" title="UN MONOLITO MODULAR PUEDE SER UNA DECISIÓN DELIBERADA" tone="success">
      Límites de dominio, ownership de migraciones y consistencia transaccional pueden ser explícitos sin pagar el costo operativo de servicios distribuidos antes de que V1 los necesite.
    </CaseStudyCard>

  </CaseStudyGrid>
</CaseStudySection>
